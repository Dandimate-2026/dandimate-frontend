| 기능 | 사용 API | 연결된 동작 |

| 플랜 선택 요청 | POST /rooms/{roomId}/plan-requests | 선택한 LITE/PRO를 targetPlan으로 전달. 선택을 바꾸면 새 대상으로 요청할 수 있다. 현재보다 낮거나 같은 플랜 요청은 비활성화한다. |

| 사진 목록 추가 조회 | GET /rooms/{roomId}/circulation?size=6&cursor=… | 첫 묶음 6장만 받고 ‘사진 더 불러오기’에서 다음 cursor 조회. 1/2/3 숫자 페이지를 유지하며, 일반 둘러보기에서는 친구 사진만 표시한다. 본인 사진은 핀 꽃에서 개별 사진으로 연다. 친구 사진이 첫 묶음에 없어도 추가 조회 가능. |

사진 한 장을 지정한 딥링크와 방 전체 통계가 필요한 기존 호출은 전체 목록 조회 helper를 유지한다. 일반 둘러보기 목록을 처음 열 때 전체 cursor를 끝까지 조회하지 않는다.

전체 알림함은 진입/앱 복귀/수동 새로고침으로 갱신한다. 계정 전체 SSE를 새로 연결한 것은 아니다. 방별 화면은 기존 방 SSE를 유지한다.

## 2. 지금 우선 필요한 신규 기능 또는 계약 보완

### A. 알림 삭제 — 테스터 피드백으로 추가된 신규 기능 요청

**요청 배경:** 테스트 중 받은 알림을 사용자가 직접 삭제하고 싶다는 테스터 의견이 있어 추가된 요구사항이다. 기존 알림 발송/읽음의 오류나 누락을 지적하는 항목과 구분한다.

**현재:** 공개 명세에는 목록 조회와 읽음만 있다. 프론트의 ‘이 기기에서 숨기기’는 서버 삭제가 아니다.

**제안:** `DELETE /notifications/{notificationId}`

- 로그인한 본인의 알림만 삭제.
- 전체 알림/방별 알림 조회에서 함께 제외.
- 읽지 않은 수와 삭제 정책을 일치시킴.
- 반복 삭제 응답 정책, 이미 삭제된 알림 처리 명시.

현재 존재하는 경로라고 가정해 프론트에서 호출하지 않았다.

### B. 템플릿 저장·조회 — 기존 방 API 확장/명세 확인

**현재:** 프론트는 `PATCH /rooms/{roomId}`에 `scrollTemplateId`를 보내고 방 홈에서 같은 필드를 읽는다. 하지만 최신 공개 명세의 PATCH 입력과 RoomSummary에는 해당 필드가 없다.

**필요한 계약:**

- PATCH 입력: scrollTemplateId 허용값과 기본값.
- 방 조회 응답: 저장된 scrollTemplateId.
- 방장만 저장, 멤버는 미리보기/요청.
- FREE/LITE/PRO별 서버 권한 검사.
- 변경 후 모든 참여자에게 갱신되는 이벤트 이름/시점.

새 URL이 필수인 것은 아니다. 서버에 이미 구현했다면 명세를 보완하고 실제 저장·새로고침·다른 기기 반영을 확인하면 된다. 현재 프론트 모의 검증만으로 실제 서버 저장을 보장하지 않는다.

### C. 웹 푸시 — 구현 유무와 공개 명세 확인

프론트는 다음 경로를 사용하지만 공개 명세에 없다.

- `GET /push/vapid-public-key`
- `POST /push/subscriptions`
- `DELETE /push/subscriptions`

배포 서버에 구현돼 있으면 요청/응답 명세를 추가한다. 없다면 구현이 필요하다. 구독 등록의 계정 연결, 중복 구독, 해제, 만료된 구독 정리와 서비스 워커가 받는 `{ title, body, url, tag }` 계약을 맞춰야 한다.

덧붙임·방장 변경·플랜 변경·재엮기 완료 알림의 enum은 이미 있다. 새 ‘알림 보내기’ API부터 만드는 대신 서버 알림 생성 → 저장 → SSE → 실제 푸시 발송 중 어디서 끊기는지 확인한다. SSE와 OS 푸시는 별개다.

### D. 사진 처리 완료 확인 — 기존 응답 보완 또는 상태 조회 API

**현재:** `POST /photos/{photoId}/complete`가 범용 Ok로만 문서화돼 있다. 프론트는 응답의 photo.status가 PROCESSING/UPLOADING이면 같은 complete를 재호출하고 READY를 기다린다.

**필요:**

- complete 응답에 photo.id/status와 상태 전이를 명시.
- 같은 complete를 반복 호출해도 되는지와 멱등성 동작 확정.
- READY 전 첫 한마디 작성 가능 여부·실패·시간 초과 처리 확정.
- POST 재호출을 피할 경우 예: `GET /photos/{photoId}`로 상태 조회 제공.

새 API가 반드시 필요한 것은 아니며, 기존 응답과 반복 호출 의미가 보장되면 그 계약으로 처리할 수 있다.

### E. 동의 버전 — 조회 경로 확인

프론트는 `GET /consents/current`를 호출하나 공개 명세에는 없다. 실패 시 v1 동의를 보낸다.

해당 API의 구현/응답을 확인하거나 버전 전달 방식을 확정해야 한다. 서비스 동의 버전이 바뀌면 고정 fallback만으로는 생성·가입·주문이 실패할 수 있다.

## 4. 제품 범위에 따라 필요한 선택적 API

- **서버에서도 답가 개념을 없앨 때:** 현재 재엮기는 `POST /paragraphs/{paragraphId}/replies`를 사용한다. 화면의 답가 목록·삭제창 제거와 서버의 답가 저장 제거는 다르다. 서버까지 없앨 경우 예: `POST /paragraphs/{paragraphId}/reweave` 계약과 기존 데이터 처리 방침이 필요하다.
- **다른 기기에서 초안 이어쓰기:** 현재 사진/녹음은 IndexedDB, 글·장소는 로컬 저장이다. 계정별 초안 조회/저장/삭제가 필요하다. 같은 기기 임시저장만이면 불필요하다.
- **첫 템플릿 안내를 계정당 한 번만:** 현재 방/멤버/기기별 localStorage다. 멤버별 templateOnboardingSeenAt 등 서버 필드가 필요하다. 방의 공통 템플릿 값과 별개다.
- **크레딧 가격을 서버에서 운영:** 주문·승인 API는 이미 연동돼 있다. 상품 목록이 프론트 상수여서 가격/묶음을 자주 변경하려면 상품 카탈로그 GET API를 추가하면 된다. 실제 결제 금액은 서버 주문 응답을 쓴다.
- **모임 시작~종료일 표시:** 현재 meetingDate 한 개에 첫날을 저장한다. 날짜 범위 표시가 필요할 때 meetingEndDate 확장.

## 5. 의도적으로 재연결하지 않은 기존 함수

- `passPhoto`: 패스 기능 제거 요구. 과거 PASSED 사진에 새 덧붙임을 쓰는 `undoPass`는 계속 사용한다.
- `skipFirstEntry`: 작성 완료 전 사진만 공개하지 않기 위한 제거.
- `deleteReply`: 답가 목록·삭제 UI 제거에 따른 미사용. 재엮기 작성 API는 여전히 사용 중이다.
- `activateReviewerDemo`: 실제 화면은 GET/PUT /reviewer-demo를 사용한다. 별도 wrapper를 다시 연결할 필요가 없다.

미사용이라는 이유만으로 제거한 기능을 다시 노출하지 않는다.
